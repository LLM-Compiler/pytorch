● I found a concrete root cause. Here's the static analysis.

  Primary bug: the launcher and the wrapper disagree about who computes what

  There is a hard contract mismatch between the two repos.

  What the Triton launcher does — in both the pool path and the fallback path,
  node_i selects only the pointer set, never the grid range:

  [&](int node_i, int local_tid, int node_threads) {
    size_t start = (N * local_tid)       / node_threads;   // no node_i
    size_t end   = (N * (local_tid + 1)) / node_threads;   // no node_i
    const std::vector<void*>& numa_ptrs = per_node_ptrs[node_i];  // node_i used
  ONLY here
    for (size_t i = start; i < end; ++i) { kernel(...); }
  }

  Within socket i, the local threads partition [0, G) among themselves — so
  every socket sweeps the entire grid. This matches Algorithm 4 in the paper
  ("each socket sweeps G").

  What the PyTorch wrapper assumes — wrapper.py:1932-1940
  (torch/_inductor/codegen/wrapper.py#L1932-L1940):

  ▎ "the Triton-CPU launcher splits the kernel grid linearly across sockets in
  ▎ row-major (M-major) tile order. Socket i therefore owns the contiguous row
  ▎ shard [i*M//W : (i+1)*M//W]"

  and it reassembles accordingly:

  out_arg[split*sid : split*(sid+1)].copy_( per_node_outs[sid][split*sid :
  split*(sid+1)] )

  That premise is false. Socket i computed all M rows; the wrapper keeps only
  rows [i·M/W, (i+1)·M/W) and discards the rest.

  Why this specifically kills 4-socket scaling

  For a row-parallel kernel, per-socket work is M · N_out · (d/W) over the full
  output grid, running on C/W cores:

  t_socket ∝ (M · N_out · d / W) / (C / W)  =  M · N_out · d / C   =  t_baseline

  The W cancels. Row-parallel kernels get zero compute scaling at any socket
  count — their entire gain comes from weight locality, not parallelism.
  Meanwhile the discarded fraction is (W−1)/W:

  ┌─────────┬────────────────────────────────┐
  │ Sockets │ Row-parallel compute discarded │
  ├─────────┼────────────────────────────────┤
  │ 2       │ 50%                            │
  ├─────────┼────────────────────────────────┤
  │ 4       │ 75%                            │
  └─────────┴────────────────────────────────┘

  At W=2, locality alone (halving remote DRAM traffic in a bandwidth-bound
  regime) is worth ~2×, so it masks the 50% waste. At W=4 locality is already
  saturated — you cannot do better than "all local" — while the waste grows to
  75% and the O(W) overheads below pile on. Net: a wash or a regression, exactly
  what you measured.

  Correctness caveat worth checking: row-block i taken from socket i contains
  only K-shard i's contribution, missing the other W−1 shards. That reads as
  numerically wrong, yet the bias handling elsewhere implies true sum semantics
  — zero_on_nonzero_nodes keeps the output bias on node 0 and zeroes it
  elsewhere (numa_attention_tp.py:1092
  (torch/_inductor/fx_passes/numa_attention_tp.py#L1092)), which is only correct
  if partials are summed. Two mechanisms in the same codebase assume opposite
  reassembly semantics. Please re-run your correctness check at W=2 — if it
  passes, my reading of which kernels reach this path is incomplete, but the
  redundant full-grid sweep is real regardless.

  The fix, either direction:
  - (a) Make the launcher split the grid across sockets — fold a global tid into
    the range so socket i sweeps only its slice. Then M-split reassembly
    becomes correct and the waste disappears.
  - (b) Keep full-grid-per-socket and replace the concat with a true Z = Σᵢ Zⁱ
    all-reduce — this is what the paper describes (Algorithm 1 line 5, Algorithm
    2 line 6).

  (a) is the smaller change and directly recovers the lost parallelism.

  Secondary findings, all O(W)

  1. Permanent pool loss on node-list mismatch — driver.py:550
  (third_party/cpu/backend/driver.py#L550). The pool is built for the first node
  list seen; any later mismatch returns nullptr and is never rebuilt, dropping
  every subsequent launch onto spawn-and-join-per-launch. This is live risk for
  you because each pass reads its own world-size knob — _numa_mlp_tp_world_size,
  _numa_attention_tp_world_size, _numa_layer_norm_tp_world_size,
  _numa_lm_head_tp_world_size. If any is left at its default while others are
  set to 4, the world sizes diverge, numa_count differs, and you silently pay
  thread construction + pthread_setaffinity_np + join on every kernel — with 4
  sockets' worth of threads. Worth logging pool == nullptr to confirm on your
  4-socket runs.

  2. Activation replication grows linearly — wrapper.py:2351-2352
  (torch/_inductor/codegen/wrapper.py#L2351-L2352). The block input is cloned to
  every socket each forward (cache=False, correctly so — it changes per
  forward). Weights are hoisted and cached, but activations are not: W full
  copies of X per NUMA block per forward. W=4 doubles this traffic versus W=2,
  and the clones run on PyTorch's unpinned OpenMP pool, so the copies themselves
  generate cross-socket traffic.

  3. Replicated normalization scales as W — Algorithm 3 duplicates the full norm
  on every socket. The paper's justification (redundant compute beats
  communication) was measured at W=2; the redundancy grows linearly with W while
  the communication it avoids does not.

  4. Grid starvation on shrinking shards — with start = G·tid/nt, any thread
  gets zero work once G < nt. Column-parallel grids shrink as 1/W, so at W=4
  with 15 cores/socket a small model (d_model 768–1280 → 320-column shards) can
  leave cores idle and pushes GEMMs into tile sizes too small to vectorize well.

  5. No NUMA-distance awareness — neither repo reads a distance matrix;
  numa_nodes[i] = i assumes shard i ↔ node i and treats all nodes as
  equidistant. That holds on a 2-socket box where remote is a single QPI/UPI
  hop. On 4-socket systems the interconnect is often a ring or
  partially-connected mesh, so "remote" is no longer uniform — some pairs are
  two hops. Your reassembly and replication traffic then pays varying, and
  sometimes double, latency that the cost model doesn't represent.

  Suggested order of attack

  Fix the launcher/wrapper contract first (finding 1) — it's the only one that
  explains a complete loss of scaling rather than a constant-factor tax, and
  it's the cheapest to change. Then instrument for finding 2, since a silent
  fallback to spawn-per-launch would compound it. Findings 3–5 are design-level
  and would shape how far NUMA-TP can scale past two sockets even once the
  contract is repaired.
